## Fixes landed THIS session (2026-07-31) - external-track metadata

User report on 0.14.1: a MangaHub title added via "Add chapter by URL" updates its
chapter count but never loads title/cover/tags; a Dynasty Reader title updates chapter
count but no cover; failure log shows `mangahub:manga:chapter: The source link cannot
be refreshed`.

Root cause: the external-track path (`capture.ts` catch -> `trackExternalChapter`),
taken when `resolveChapter` is bot-blocked, had two gaps:

1. The created **source link had no `sourceMangaId`**, so `listMangaChapters`
   (`sources.ts`) threw "The source link cannot be refreshed" on every background
   update. Chapter count only ever appeared because `scheduleChapterListRefresh`
   primes the list once at add-time.
2. **No metadata was ever fetched** on that path - title stayed a humanized slug,
   no cover.

Changes (all CI-green, `npm run check` EXIT=0, with regression tests):

- `database.ts trackExternalChapter`: the created manga AND source link now carry
  `sourceMangaId` from `input.mangaInfo`. Test in `database.test.ts`
  ("persists sourceMangaId on the created manga AND source link").
- `sources.ts listMangaChapters`: when a link lacks `sourceMangaId`, recover it from
  the link URL via the adapter's `parseMangaUrl` before throwing - heals legacy
  external links with zero user action. Tests in `sources.test.ts`
  ("listMangaChapters sourceMangaId heal", 2 cases).
- `sources.ts resolveMangaMetadata` (new): best-effort `resolveManga` to pull the
  real title/cover from the manga page (often reachable even when the chapter page
  is gated). Genres left to `backfillMangaGenres`.
- `capture.ts refreshExternalMangaMetadata`: on a NEW external-tracked title
  (`tracked.created`) with `mangaInfo`, best-effort update title/cover + cache cover.
- `updates-sources.ts backfillMangaGenres`: now also backfills a **missing cover**
  (via `resolveCoverFor`) in the same rate-limited pass, not just genres. This is
  what heals the Dynasty Reader case (dynasty has `resolveCover` but the one-shot
  cover fetch inside `resolveChapter` can fail, and nothing re-fetched it). Runs on
  background startup/install.

## New source: MangaKatana (added 2026-07-31)

Full adapter `packages/sources/src/mangakatana.ts`, capabilities `["pages","chapters"]`
(full in-app reader). Verified against live HTML: 142 chapters, 55 page images, title/
cover/genres, 42 search results.

- URL shapes: manga `/manga/{slug}.{numericId}`, chapter `/manga/{slug}.{numericId}/c{n}`.
  sourceMangaId = the whole `{slug}.{numericId}` token.
- Page images: a JS array `var <random>=[ '<i*.mangakatana.com token url>', ... ]`. The
  page ships a 1-entry DECOY array with randomised var names, so extractImages picks the
  LONGEST array of CDN image URLs.
- Chapter number comes from the visible "Chapter N" label (isolated via regex, since
  parseChapterNumber wants an isolated token), URL c-number as fallback; unnumbered rows
  interpolated via assignListSortKeys("newest-first").
- Registered in `packages/sources/src/index.ts`; permissions in
  `apps/extension/src/permissions.ts` (`https://mangakatana.com/*`, `www`, and
  `*://*.mangakatana.com/*` for the i1/i2 image CDN); health-target added; manifest-policy
  test snapshot (`tooling/browser-tests/src/manifest-policy.test.js`) updated.
- Tests: `packages/sources/src/mangakatana.test.ts`.
- DESIGN RISK (not fixed): sourceMangaId includes the slug, so a site slug-rename (numeric
  id kept) makes a new id -> possible duplicate entry. Shared by all slug-id adapters; the
  library cleanup/merge tool can absorb it. Revisit only if it bites in the field.

## /bughunt results (2026-07-31) - 4 hunters, all fixes landed CI-green

Ran after mangakatana + the metadata fixes. 5 confirmed bugs, each fixed with a
regression test; `npm run check` EXIT=0 (extension 427, sources 176).

1. [numeric] mangakatana: `parseChapterNumber("Chapter 5")` = NaN, so the "authoritative
   label" path was dead and sortKey always came from the URL c-number (wrong on a
   re-slug/renumber). Fixed: `chapterNumberFromLabel` isolates the number from the label +
   `assignListSortKeys`. (mangakatana.test.ts "chapter numbering")
2. [data] `trackExternalChapter` found-branch never backfilled sourceMangaId onto a
   fallback-matched legacy record even when correct mangaInfo was in hand -> stayed flagged
   fallback-created forever. Fixed: backfill manga + link in the `else if` branch.
   (database.test.ts "backfills sourceMangaId onto a fallback-matched legacy record")
3. [async] `refreshExternalMangaMetadata` unconditionally overwrote the humanized title
   with resolveManga's title, which some adapters return as a raw slug on parse-miss
   (comix -> "solo-leveling-season-2"). Fixed: `isSlugLikeTitle` guard keeps the humanized
   title. (background/capture.test.ts)
4. [async] `cacheCover` orphaned a covers row if the manga was deleted mid-refresh. Fixed
   at the root: cacheCover now writes inside a `[manga,covers]` transaction and no-ops if
   the manga is gone. (database.test.ts "cacheCover orphan guard")
5. [async] `backfillMangaGenres` didn't re-check the abort flag between the genre and the
   new cover branch, costing one extra cover fetch + 350ms per abort. Fixed: added
   `if (genreBackfillAborted) break` before the cover branch. (updates-sources.test.ts)

Dropped (probed, not real): Infinity-sort NaN (V8 keeps finite order correct + checkUpdates
is finite-guarded); listMangaChapters malformed-URL crash (already inside try/catch);
extractGenres nested-div truncation (real markup is flat, matches madara convention -
watch item only).
